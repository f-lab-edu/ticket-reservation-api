# 유스케이스 시나리오

## 1. 회원 관리

### UC-01. 이메일 중복 확인

- **액터:** 비회원
- **선행 조건:** 없음
- **성공 시나리오**
  1. 비회원이 가입에 사용할 이메일의 중복 확인을 요청한다.
  2. 시스템은 해당 이메일로 가입된 회원이 있는지 확인한다.
  3. 시스템은 이메일 사용 가능 여부를 반환한다.
- **확장**
  - **2a. 이미 가입된 이메일인 경우:** 시스템은 이메일 사용이 불가능하다는 결과를 반환한다.
  - **2b. 이메일이 입력되지 않은 경우:** 시스템은 요청을 거절한다.

### UC-02. 이메일 회원 가입

- **액터:** 비회원
- **선행 조건:** 없음
- **성공 시나리오**
  1. 비회원이 이메일과 비밀번호로 회원 가입을 요청한다.
  2. 시스템은 필수 입력값을 확인한다.
  3. 시스템은 해당 이메일의 중복 여부를 확인한다.
  4. 시스템은 회원 정보를 저장한다.
  5. 시스템은 가입 성공 결과를 반환한다.
- **확장**
  - **2a. 필수 입력값이 누락된 경우:** 시스템은 가입 요청을 거절한다.
  - **3a. 이미 가입된 이메일인 경우:** 시스템은 가입 요청을 거절한다.
  - **4a. 회원 정보 저장에 실패한 경우:** 시스템은 가입 실패 결과를 반환한다.

### UC-03. 로그인

- **액터:** 비회원
- **선행 조건:** 가입된 계정이 존재한다.
- **성공 시나리오**
  1. 비회원이 이메일과 비밀번호로 로그인을 요청한다.
  2. 시스템은 해당 이메일의 회원 계정을 조회한다.
  3. 시스템은 비밀번호가 일치하는지 확인한다.
  4. 시스템은 인증 정보를 발급한다.
  5. 시스템은 로그인 성공 결과를 반환한다.
- **확장**
  - **2a. 가입된 회원 계정이 없는 경우:** 시스템은 로그인을 거절한다.
  - **3a. 비밀번호가 일치하지 않는 경우:** 시스템은 로그인을 거절한다.
  - **4a. 인증 정보 발급에 실패한 경우:** 시스템은 로그인 실패 결과를 반환한다.

## 2. 공연 관리

### UC-04. 예약 가능한 공연 목록 조회

- **액터:** 비회원, 회원, 관리자
- **선행 조건:** 없음
- **성공 시나리오**
  1. 액터가 예약 가능한 공연 목록을 요청한다.
  2. 시스템은 현재 판매 기간 내에 있고 잔여 판매 수량이 있는 공연을 조회한다.
  3. 시스템은 공연 목록을 반환한다.
- **확장**
  - **2a. 조회 결과가 없는 경우:** 시스템은 빈 목록을 반환한다.

### UC-05. 전체 공연 목록 조회

- **액터:** 비회원, 회원, 관리자
- **선행 조건:** 없음
- **성공 시나리오**
  1. 액터가 전체 공연 목록을 요청한다.
  2. 시스템은 등록된 공연 목록을 조회한다.
  3. 시스템은 공연 목록을 반환한다.
- **확장**
  - **2a. 등록된 공연이 없는 경우:** 시스템은 빈 목록을 반환한다.

### UC-06. 공연 상세 조회

- **액터:** 비회원, 회원, 관리자
- **선행 조건:** 조회할 공연이 존재한다.
- **성공 시나리오**
  1. 액터가 특정 공연의 상세 정보를 요청한다.
  2. 시스템은 해당 공연의 상세 정보를 조회한다.
  3. 시스템은 공연 상세 정보를 반환한다.
- **확장**
  - **1a. 조회 대상 공연이 존재하지 않는 경우:** 시스템은 조회 실패 결과를 반환한다.

### UC-07. 공연 등록

- **액터:** 관리자
- **선행 조건:** 관리자가 인증되었으며 공연 등록 권한을 보유한다.
- **성공 시나리오**
  1. 관리자가 공연 정보를 입력해 등록을 요청한다.
  2. 시스템은 필수 입력값과 입력 정보의 유효성을 확인한다.
  3. 시스템은 공연 정보를 저장한다.
  4. 시스템은 등록 성공 결과를 반환한다.
- **확장**
  - **2a. 필수 입력값이 누락된 경우:** 시스템은 등록 요청을 거절한다.
  - **2b. 판매 시작 시각이 판매 마감 시각보다 늦거나 같은 경우:** 시스템은 등록 요청을 거절한다.
  - **2c. 판매 수량이 유효하지 않은 경우:** 시스템은 등록 요청을 거절한다.
  - **3a. 공연 정보 저장에 실패한 경우:** 시스템은 등록 실패 결과를 반환한다.

### UC-08. 공연 정보 수정

- **액터:** 관리자
- **선행 조건:** 관리자가 인증되었으며 공연 수정 권한을 보유한다. 수정 대상 공연이 존재한다.
- **성공 시나리오**
  1. 관리자가 수정할 공연을 선택한다.
  2. 관리자가 변경할 공연 정보를 입력해 수정을 요청한다.
  3. 시스템은 수정 대상의 존재 여부, 수정 항목의 유효성, 예약 존재 여부에 따른 변경 제한 및 총 판매 수량 제약을 검증한다.
  4. 시스템은 공연 정보를 수정한다.
  5. 시스템은 수정 성공 결과를 반환한다.
- **확장**
  - **3a. 수정 대상 공연이 존재하지 않는 경우:** 시스템은 수정 요청을 거절한다.
  - **3b. 수정 항목의 유효성 검증에 실패한 경우:** 시스템은 수정 요청을 거절한다.
  - **3c. 예약이 존재하고 공연 일시 또는 판매 시작 일시를 변경하려는 경우:** 시스템은 수정 요청을 거절한다.
  - **3d. 예약이 존재하고 판매 종료 일시를 기존 값보다 앞당기려는 경우:** 시스템은 수정 요청을 거절한다.
  - **3e. 변경하려는 총 판매 수량이 결제 대기 및 예약 확정 상태의 예약 수량 합계보다 적은 경우:** 시스템은 수정 요청을 거절한다.
  - **4a. 공연 정보 수정에 실패한 경우:** 시스템은 수정 실패 결과를 반환한다.

## 3. 예약 관리

### UC-09. 예약 신청

- **액터:** 회원, 관리자
- **선행 조건:** 액터가 인증된 상태이며 예약 대상 공연이 존재한다.
- **성공 시나리오**
  1. 액터가 예약할 공연과 수량을 지정해 예약을 요청한다.
  2. 시스템은 공연의 판매 기간과 잔여 판매 수량을 확인한다.
  3. 시스템은 요청 수량이 유효한지 확인한다.
  4. 시스템은 예약 당시 티켓 가격과 예약 금액을 기록하고 예약 상태를 결제 대기로 설정한다.
  5. 시스템은 결제 제한 시각을 결정한다.
  6. 시스템은 예약 수량만큼 잔여 판매 수량을 차감한다.
  7. 시스템은 예약 성공 결과를 반환한다.
- **확장**
  - **2a. 판매 기간이 아니거나 잔여 판매 수량이 없는 경우:** 시스템은 예약 요청을 거절한다.
  - **3a. 요청 수량이 1 미만이거나 잔여 판매 수량을 초과하는 경우:** 시스템은 예약 요청을 거절한다.
  - **4a. 예약 정보 저장에 실패한 경우:** 시스템은 예약 요청을 실패 처리한다.
  - **6a. 동시 요청 등으로 잔여 판매 수량이 부족해진 경우:** 시스템은 예약 요청을 실패 처리하고 데이터 정합성을 유지한다.

### UC-10. 예약 목록 조회

- **액터:** 회원, 관리자
- **선행 조건:** 액터가 인증된 상태다.
- **성공 시나리오**
  1. 액터가 본인의 예약 목록을 요청한다.
  2. 시스템은 해당 액터의 예약 내역을 조회한다.
  3. 시스템은 예약 목록을 반환한다.
- **확장**
  - **2a. 예약 내역이 없는 경우:** 시스템은 빈 목록을 반환한다.

### UC-11. 예약 상세 조회

- **액터:** 회원, 관리자
- **선행 조건:** 액터가 인증된 상태다.
- **성공 시나리오**
  1. 액터가 특정 예약의 상세 정보를 요청한다.
  2. 시스템은 예약의 존재 여부와 조회 권한을 확인한다.
  3. 시스템은 예약 상세 정보를 반환한다.
- **확장**
  - **2a. 예약이 존재하지 않는 경우:** 시스템은 조회 실패 결과를 반환한다.
  - **2b. 다른 회원의 예약인 경우:** 시스템은 조회를 거절한다.

### UC-12. 예약 취소

- **액터:** 회원, 관리자
- **선행 조건:** 액터가 인증된 상태이며 취소 대상 예약이 존재한다.
- **성공 시나리오**
  1. 액터가 본인의 예약 취소를 요청한다.
  2. 시스템은 예약의 존재 여부와 취소 요청자의 권한을 확인한다.
  3. 시스템은 예약 상태가 결제 대기 또는 예약 확정인지 확인한다.
  4. 시스템이 현재 시각이 공연 판매 종료 일시 이전인지 확인한다.
  5. 예약 상태가 예약 확정이면 시스템은 Mock 결제 취소를 수행한다.
  6. 예약 상태가 결제 대기이거나 Mock 결제 취소가 성공했으면 시스템은 예약 상태를 취소로 변경한다.
  7. 시스템은 취소된 예약이 확보한 티켓 수량을 다시 판매할 수 있도록 처리한다.
  8. 시스템은 취소 성공 결과를 반환한다.
- **확장**
  - **2a. 예약이 존재하지 않거나 다른 회원의 예약인 경우:** 시스템은 취소 요청을 거절한다.
  - **3a. 예약 상태가 결제 대기 또는 예약 확정이 아닌 경우:** 시스템은 취소 요청을 거절한다.
  - **4a. 공연 판매 종료 시각에 도달했거나 지난 경우:** 시스템은 취소 요청을 거절한다.
  - **5a. Mock 결제 취소에 실패한 경우:** 시스템은 예약 상태와 판매 가능 수량을 변경하지 않고 취소 실패 결과를 반환한다.
  - **6a. 결제 또는 만료 처리와 동시에 요청이 발생해 예약 상태를 변경할 수 없는 경우:** 시스템은 취소 요청을 거절하고 수량이 중복 복원되지 않도록 한다.
  - **7a. 예약 취소 처리에 실패한 경우:** 시스템은 예약 상태와 판매 수량의 정합성을 유지하도록 처리한다.
  - **참고:** 실제 결제 금액의 환불은 처리하지 않는다.

### UC-13. 예약 만료 처리

- **액터:** 예약 만료 처리 스케줄러
- **선행 조건:** 결제 대기 상태의 예약이 존재한다.
- **성공 시나리오**
  1. 시스템은 결제 제한 시각이 도래한 결제 대기 예약을 확인한다.
  2. 시스템은 예약 상태를 만료로 변경한다.
  3. 시스템은 만료된 예약이 확보한 티켓 수량을 다시 판매할 수 있도록 처리한다.
- **확장**
  - **2a. 예약 상태가 이미 변경된 경우:** 시스템은 해당 예약을 중복 만료 처리하지 않는다.
  - **3a. 만료 처리에 실패한 경우:** 시스템은 예약 상태와 판매 수량의 정합성을 유지할 수 있도록 처리한다.

## 4. 결제 관리

### UC-14. 결제

- **액터:** 회원, 관리자
- **선행 조건:** 액터가 인증된 상태이며 본인의 결제 대기 상태 예약이 존재한다.
- **성공 시나리오**
  1. 액터가 본인의 예약에 대한 결제를 요청한다.
  2. 시스템은 예약의 소유자와 현재 상태를 확인한다.
  3. 시스템은 현재 시각이 결제 제한 시각 이전인지 확인한다.
  4. 시스템은 Mock 결제를 수행한다.
  5. Mock 결제 성공 시 시스템은 예약 상태를 예약 확정으로 변경한다.
  6. 시스템은 결제 결과를 반환한다.
- **확장**
  - **2a. 예약이 존재하지 않거나 다른 회원의 예약인 경우:** 시스템은 결제 요청을 거절한다.
  - **2b. 예약 상태가 결제 대기가 아닌 경우:** 시스템은 결제 요청을 거절한다.
  - **3a. 현재 시각이 결제 제한 시각과 같거나 이후인 경우:** 시스템은 결제 요청을 거절한다.
  - **4a. Mock 결제 실패 결과를 받은 경우:** 예약 상태를 취소로 변경하고 확보한 티켓 수량을 복구한다.
  - **5a. 결제 요청과 예약 취소 또는 만료 처리가 동시에 발생해 예약 상태를 변경할 수 없는 경우:** 시스템은 예약 상태와 결제 결과의 정합성을 유지하고 중복 수량 복원이 발생하지 않도록 처리한다.
  - **5b. 결제 성공 후 예약 확정 처리에 실패한 경우:** 시스템은 결제 결과와 예약 상태가 불일치하지 않도록 처리한다.
